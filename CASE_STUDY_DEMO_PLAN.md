## 1. Executive Summary

Build a **deterministic, discrete-event multi-node blockchain simulator in pure Go** that models block gossip propagation, configurable network stress (latency, propagation delay, peer churn, load), detects temporary forks, logs events, generates a labeled dataset, and trains **fork-risk prediction models in Go** (Logistic Regression baseline + Random Forest candidate). Output: reproducible CLI experiments, CSV datasets, PNG charts, and a measurable improvement over a naive baseline.

Everything runs in a single Go module — simulation, ML, metrics, visualization. No Python, no external simulators, no Docker required.

**Review update (v1):** The plan now explicitly (1) includes a dynamic-network experiment with mid-run condition changes to validate genuine future prediction; (2) formally distinguishes fork births, fork episodes, stale blocks, and reorganizations with validation targets; (3) separates transaction arrival/processing load from block-production frequency; (4) strengthens ML evaluation with run-level/scenario-held-out splits, a meaningful rule-based baseline, and leakage/counterfactual safeguards; (5) retains Go-only with the CLI-first dashboard optional.

## 2. Research Problem

- **Temporary fork:** two or more valid competing blocks exist at the same height across node views because propagation hasn't converged; resolved later by longest-chain selection, producing stale blocks and possible reorgs.
- **Causes studied:** near-simultaneous proposals + propagation delay + peer unavailability + load.
- **Prediction target:** at time *t*, predict whether ≥1 fork occurs within the next **H = 3 blocks** (sensitivity checked for H=1..5).
- **Labels:** generated by scanning future fork events; features strictly computed from events ≤ *t* (leakage prevention).
- **Can establish:** correlation between observable network state and near-future fork occurrence; predictive model performance envelope.
- **Cannot establish:** causation on real networks, real consensus-implementation behavior, production applicability.

**Component responsibilities**
1. **Config loader** — scenario params → typed config structs; validated.
2. **Event queue** — binary min-heap keyed by (time, seq) for total-order determinism.
3. **Node state** — per-node chain, mempool counters, peer set, tip height.
4. **Network model** — delay sampling (Gamma/lognormal), bandwidth factor, per-peer link states.
5. **Churn model** — Markov on/off per node with rates from config.

11. **Analyzer/Viz** — scenario aggregation, gonum/plot PNGs.

## 5. Simulation Design (Determinism Strategy)

## 5.1 Baseline Models

- **Decker–Wattenhofer Formula**: For a block that takes `τ` seconds to propagate and a target block interval `T` the theoretical probability of a fork is `r = 1 - exp(-τ / T)` under a Poisson arrival assumption. The simulator uses a deterministic inter‑block time of `T`, optionally perturbed by a jitter term.  The formula above matches the simulator when the jitter is negligible and the arrivals are treated as a Poisson process.
- **Persistence baseline**: Always predict a fork if a *fork birth* has occurred in the last `k` blocks (parameter `k` to be tuned).
- **Hybrid baseline**: Use `p̂` from the Decker formula as an additional feature fed into the logistic regression / random forest.
- **Other baselines**: The same persistence, hybrid and the analytical baseline are all included in the training split and reported in the evaluation tables.

- **Event loop:** all "activity" is events in one global min-heap: `Propose`, `Gossip{from,to,block}`, `Arrive`, `ChurnToggle`, `TipAdopt`. Processing pops the earliest event; tie-break by sequence number → identical seeds produce byte-identical logs.
- **Delay model:** link delay = f(base latency, jitter, bandwidth), sampled per message from Gamma(mean μ, shape k) where μ,k come from config; stream-seeded per node pair.
- **Block production:** target interval T (e.g., 1s); proposal jitter uniform/Gaussian; blocks carry a proposer ID, height, parent hash, tx count.
- **Chain rule:** longest chain; tie-break by lowest block hash (deterministic).
- **Fork definition (mechanical):** a *fork event* = a `TipAdopt` that switches to a branch not containing the node's previous tip while a competing valid block at the same height exists in the node's view; aggregated across nodes → network-level fork episode. Stale blocks and reorg depth derived from the same log.
- **Warm-up:** first 1,000 blocks discarded from metrics/dataset.
- **Scale:** default 10 nodes, 10,000 blocks/run; ~1.8M blocks total across the full matrix — Go easily handles this; measured in the Milestone 1 smoke test.

## 6. Experimental Matrix

### Adaptive‑Conformal Drift Handling
- **Fixed sliding-window parameters (conservative defaults):** window size = 100 blocks, threshold = 2.0 standard deviations from rolling mean. Tuning method: grid search over window sizes [50, 100, 200] and thresholds [1.5, 2.0, 2.5]σ on validation data from baseline scenario, selecting parameters maximizing drift detection F1 score with false positive rate < 5% on stationary data.
- Implementation: `internal/ml/drift/sliding_window.go` provides core detector; Page-Hinkley and ADWIN are optional extensions documented in `internal/ml/drift/README.md` but not required for core deliverables.
- Reproducibility: detector configuration is scenario YAML field; unit tests verify detection of synthetic drift points and stability on stationary streams.

| Scenario | Independent variable | Controlled (fixed) | Reps | Seeds |
|---|---|---|---|---|
| Baseline | none | latency 50±10ms, prop 100±20ms, uptime 99%, 10 nodes, T=1s | 30 | 1–30 |
| Latency stress | mean latency 50→300ms (calibrated operational regime) | rest of baseline | 30 | 1–30 |
| Propagation stress | mean propagation 100→1000ms | rest of baseline | 30 | 1–30 |
| Churn stress | uptime 99%→50–85%, churn rate ×3 | rest of baseline | 30 | 1–30 |
| **Block-rate stress** | block interval multiplier 1.0→5.0 (T=1s→0.2s, production ↑, saturation expected) | rest of baseline | 30 | 1–30 |
| **Tx-load stress** | tx arrival rate ×1→×10 (~100 offered tx/s, capacity 10), block interval fixed 1s (under-filled vs saturated) | rest of baseline | 30 | 1–30 |
| Combined | latency+propagation+block-rate scaled together | uptime 99% | 30 | 1–30 |
| **Dynamic network** | **Latency shift: 50ms→300ms (t=5k blocks in 10k production; block 150 in 300s pilot)** | **Baseline pre/post** | **30** | **1–30** |

- **Independent variables** = the stress parameter(s). **Dependent** = fork rate, reorg depth, propagation time, stale rate, node-view consistency, prediction metrics. **Controlled** = all other params, seeds, run length.
- **Latency Stress Calibration Rationale (50ms → 300ms):** While originally scoped as 500 ms in initial drafts, empirical verification and analytical modeling (see `docs/decisions.md` D19, D22) showed that at 500 ms mean latency with 100 ms propagation delay (600 ms delay per hop) on a 10-node ring+forward topology (diameter 3–4 hops), end-to-end propagation time is 1.8–2.4 s, severely exceeding the 1.0 s block interval. This produces continuous, degenerate chain fragmentation where nodes never converge. A 300 ms mean latency (400 ms per hop) stresses the consensus engine significantly (empirical fork rate 12–20%, theoretical Decker rate ~33%) while preserving an observable, non-degenerate consensus regime. In addition, 300 ms aligns directly with the post-transition regime of `dynamic_network` (50 ms → 300 ms) and `combined_stress` (300 ms latency), enabling rigorous cross-scenario comparison.
- **Parameter Adjustments & Metric Implications:**
  - *Latency Jitter (30 ms at 300 ms mean):* Scaled proportionally to maintain a realistic coefficient of variation (10%) under the Gamma distribution model. Metric implication: realistic tail delays without negative delay clipping.
  - *Propagation Jitter (100 ms at 1000 ms mean):* Scaled proportionally (10% of mean) in `propagation_stress` to reflect queuing delay variance.
  - *Settlement Grace Extension (10s → 30s):* In `propagation_stress` and `combined_stress`, `settlement_grace_sec` is extended to 30.0 s. High one-way delays require more simulated settlement time after proposal cessation to allow all in-flight gossip messages to arrive and settle. Without this grace extension, blocks near the end of the simulation would be cut off before reaching peer nodes, artificially inflating stale rates and undercounting settled forks.
  - *Block Jitter (0.1s → 0.02s):* Scaled with `block_interval_sec` (0.2s) in `block_rate_stress` to keep proposal jitter at 10% of interval and avoid interval inversion.
- **Dynamic network experiment:** conditions change mid-run (after warm-up); tests whether features from before the shift predict post-shift fork behavior — a genuine prediction test rather than a stationary fit. Seeds 1–30 shared with baseline so the pre-shift segments are exact replays. In full-scale 10,000-block production experiments, the transition occurs at block 5,000. In 300-second pilot runs (~300 blocks), the transition occurs at block 150 (midpoint of the pilot run).
- **Transaction-load separation & Decoupled Poisson Arrival Model:**
  - In earlier iterations, transaction counts were coupled to block proposal events, which erroneously inflated transaction arrival rates by 5× when reducing `block_interval_sec` from 1.0 s to 0.2 s in `block_rate_stress`.
  - Under the decoupled arrival model, transactions arrive into an independent network-wide mempool (`txPool`) according to a Poisson arrival process driven by `rngTx` with arrival rate $\lambda = \text{tx\_arrival\_rate} \times \text{tx\_per\_block}$ (transactions per simulated second).
  - **Block Capacity Semantics (`block_capacity`):**
    - `block_capacity: 0` means **unlimited transactions per block**. Proposed blocks consume the entire pending mempool (`txPool`) without an artificial cap.
    - `block_capacity > 0` enforces a strict ceiling on transactions included per proposed block ($\min(\text{txPool}, \text{block\_capacity})$). Excess transactions remain in `txPool` and are preserved.
  - **Explicit Zero Arrival Rate:** An explicit YAML setting of `tx_arrival_rate: 0` (or `0.0`) remains 0.0 (disabling arrivals), while omitted values default to 1.0. Negative rates are rejected.
  - In `block_rate_stress` ($T = 0.2\text{ s}$, `tx_arrival_rate = 1.0`): Offered load remains ~10 tx/s (identical to baseline), so blocks take ~2 transactions each instead of inflating throughput.
  - In `tx_load_stress` ($T = 1.0\text{ s}$, `tx_arrival_rate = 10.0`, `block_capacity = 10`, `tx_per_block = 10`): Offered load scales to ~100 offered tx/s while blocks take at most 10 transactions each, producing a persistent queue backlog of ~90 tx/s (actual measured throughput ~9.66 raw tx/s) and satisfying the saturation definition.
  - Conservation Invariant: $\text{TotalOfferedTx} = \text{TotalProcessedTx} + \text{FinalPendingTx}$ holds strictly at every simulation step.
  - **Transaction-Load Modeling Scope & Limitation:** Transaction arrivals are modeled independently of block-production frequency, and positive `block_capacity` demonstrates mempool queue saturation. However, in the current simulator, block payloads/transaction counts are **not** coupled to network block payload size or message propagation delays. The current results do **not** establish that higher transaction load itself causes higher fork rates through transmission latency; modeling payload-dependent delays is reserved as a future model extension.
  - Output Directories: `outputs/pilot_final/` contains the authoritative final pilot CSV and report; `outputs/pilot/` retains historical evidence; `outputs/runs/historical_incomplete/` retains early prototype event logs lacking metadata.
- Do **not** assume monotonic increases — report measured results; a pilot sweep (Milestone 1 verification) confirms the baseline produces forks at a non-trivial rate; if not, the T/delay ratio is retuned and the change documented.

## 7. Metrics & Formulas

| Metric | Formula / definition |
|---|---|
| Fork rate | fork episodes ÷ total blocks (post warm‑up) |
| Propagation time | per block: last‑node arrival − proposal time (mean, p95) |
| Confirmation latency | time from proposal until tip stable for K blocks |
| **Raw TPS** | total transactions produced ÷ simulated time |
| **Goodput** | finalized (non‑stale) transactions ÷ simulated time |
| Stale/orphan rate | stale blocks ÷ total blocks |
| Reorg depth | height distance of tip switch after convergence |
| Node‑view consistency | % nodes sharing the majority tip, sampled per block |
| Peer availability | time‑weighted % uptime |
| Prediction latency | wall‑clock inference time per sample (ms) |

**Distinctions:** The raw TPS counts every transaction generated by the simulator, whereas goodput only counts those that were included in the final chain and were not later orphaned. The trade‑off curve will be plotted as *raw TPS* vs *fork rate* and *goodput* vs *fork rate* in both the case‑study and end‑semester reports.

## Saturation Definition

- **Definition:** Offered transaction load (tx arrival rate × avg tx size) exceeds block‑processing capacity (block size / block interval).
- **Classification:**
  - **Saturated:** offered load ≥ capacity → queues form, goodput plateaus, increased latency.
  - **Under‑filled:** offered load < capacity → no persistent queues, goodput limited only by arrival rate.
- **Usage:** In the simulator, each block logs `offered_tx_load` and `processed_tx_load`. The saturation flag is set when offered_load ≥ capacity.
- **Purpose:** Provides clear operational characterization for the stress scenarios and for comparison metrics.

## 8. Dataset Schema & Labeling

`fork_risk_dataset.csv` — one row per (run, block index *t*), *t* > warm-up, *t* ≤ N−H:

### Prediction Problem Definition & Sampling Unit
- **Sampling Unit:** Exactly one sample per eligible unique run/block-height ($t \in (\text{warmUpBlocks}, N - H]$).
- **Prediction-Time Anchor:** Anchored to the first `BlockPropose` event at block height $t$ (simulation time $T_t$). Multiple competing proposal events at the same block height are not emitted as separate dataset rows.
- **Observation Window:** Strictly past events $\le T_t$ (`SimTime <= T_t`). Future events ($> T_t$) are strictly excluded to prevent data leakage.
- **Forecast Horizon:** $H = 3$ block heights (predicts whether $\ge 1$ new fork birth occurs within blocks $t+1, t+2, t+3$).
- **Label Definition:** Using the authoritative `fork.Detector` as source of truth:
  - $\text{label} = 1$ if at least one fork episode has its birth at height $h \in (t, t+H]$ or birth time in $[T_{t+1}, T_{t+H}]$.
  - $\text{label} = 0$ otherwise.
- **Unresolved Fork Episodes:** Handled consistently: if a fork episode was born in $(t, t+H]$ but unresolved by simulation end, it still represents a genuine fork birth and is labeled 1.
- **Boundary Handling & Censoring:** Any block proposal with $t \le \text{warmUpBlocks}$ (warm-up) or $t > N - H$ (where $N$ is final proposed block height) is censored and omitted because its full $H$-block horizon is not observable.
- **Node Availability:** Evaluated dynamically; node status changes (`ChurnToggle` events with `node_id` and `reason`) are captured as engineered features (`peer_connectivity`, `churn_rate_100`).

### Canonical Feature Schema (`v1.3`)

The prediction dataset `outputs/ml/dataset/fork_risk_dataset.csv` contains exactly **28 columns** (5 metadata columns, 22 engineered features, and 1 binary forecast label).

#### Rolling-Window Semantics & Boundary Handling
The feature extractor operates on ordered historical events up to prediction time $T_t$ (`currentIdx`):
1. **Proposal-Record Windows (Exactly 10 proposals):**
   - Sliced via `proposals[max(0, currentIdx-9) : currentIdx+1]`.
   - Contains at most 10 proposal records (exactly 10 whenever `currentIdx >= 9`).
   - Used for: `stale_rate_10`, `latency_mean_10`, `latency_var_10`, `prop_time_mean_10`, `fork_count_10`, `reorg_count_10`, `tx_backlog_growth_10`, and `processed_tps_10`.
   - *Stale Rate Semantics:* Evaluated as `staleCount / len(recentProposals)`. A block is stale if it does not belong to the canonical chain traced from the majority tip of nodes at `maxHeight` at prediction time $T_t$.
2. **Interval Windows (10 Intervals from 11 Proposal Timestamps):**
   - Sliced via `proposals[max(0, currentIdx-10) : currentIdx+1]`.
   - Contains up to 11 proposal timestamps, yielding up to 10 consecutive inter-block intervals ($T_i - T_{i-1}$).
   - Used for: `avg_block_interval_10` and `block_interval_var_10`.
3. **Churn Windows (Unique Block Heights):**
   - Sized across unique block heights observed up to $T_t$ ($M = \text{len}(uniqueHeights)$).
   - *Full Window ($M \ge 100$):* Starts at the earliest proposal time of $uniqueHeights[M-100]$. Denominator is $100.0$.
   - *Early-Run Window ($M < 100$):* Starts at $0.0$ (simulation start, capturing all initial churn events). Denominator is $M$ (available unique heights).
   - Events on exact boundaries ($T_{\text{start}} \le T_e \le T_{\text{pred}}$) are included.
   - Unit: **churn events per block**.
4. **Causal Truncation:**
   - Evaluated strictly on records with `SimTime <= T_t`.

## 9. ML Plan & Implementation (in Pure Go)

- **Model A — Logistic Regression (Baseline):**
  - Binary classifier with sigmoid output $\hat{p} = \sigma(w^T x_{\text{scaled}} + b)$.
  - Binary cross-entropy loss with $L_2$ regularization ($\lambda = 0.001$).
  - Mini-batch gradient descent with Adam optimizer (learning rate $\eta = 0.05$, early stopping patience 25 epochs).
  - Class weighting to balance minority class: $w_{\text{pos}} = N_{\text{neg}} / N_{\text{pos}}$.
  - Standard Scaler (z-score) fitted strictly on training data only.
- **Model B — Random Forest (Candidate):**
  - Custom pure-Go CART + Bagging ensemble (50 trees, max depth 8, min samples split 5).
  - $m_{\text{try}} = \lfloor \sqrt{D} \rfloor$ random feature subsampling at each node.
  - Gini impurity reduction split criterion with class weighting.
  - Independent deterministic random streams via `math/rand/v2` with `NewPCG(seed, treeIndex)`.
  - Zero unmaintained dependencies (clean pure-Go replacement for stale `golearn`).
- **Baseline Models:**
  - **Baseline 1 (Prevalence):** Predicts constant training class prevalence ($\hat{p} = 0.5182$).
  - **Baseline 2 (Heuristic):** Causal rule-based detector triggering on `competing_tips > 1` or `recent_fork_count > 0` ($\hat{p} = 0.80$ if triggered, $0.20$ otherwise).
- **Run-Level Splitting (Leakage-Proof):**
  - Groups rows strictly by simulation run (`run_id`).
  - Train: Seed 1 runs (8 runs, 1,565 rows).
  - Validation: Seed 2 runs (8 runs, 1,085 rows, used for threshold tuning and early stopping).
  - Held-Out Test: Seed 3 runs (8 runs, 1,608 rows, completely independent random realizations across all 8 scenarios).
- **Evaluation Criteria:**
  - Accuracy alone is misleading due to wide scenario prevalence swings (10% to 85%).
  - Evaluated on **ROC-AUC, PR-AUC, F1 Score, Precision, Recall, Confusion Matrix, and Brier Score** (calibration).
  - Threshold tuned strictly on validation set: $\tau^*_{\text{LR}} = 0.25$, $\tau^*_{\text{RF}} = 0.20$.
- **Model Persistence & CLI:**
  - Models serialized to JSON (`outputs/ml/models/logistic_regression/model.json`, `outputs/ml/models/random_forest/model.json`).
  - Schema, scaling parameters, feature ordering, and weights fully persisted and reloadable without retraining.
  - Dedicated CLI binaries: `cmd/dataset`, `cmd/split`, `cmd/train`, `cmd/evaluate`, `cmd/drift`, `cmd/predict`.
